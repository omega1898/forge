## Ada / SPARK: standards (AQ&S, TR 15942, TR 24772-2), GNAT warnings/style/restrictions, SPARK/GNATprove, GNATcheck, AdaControl

### Takeaway
The deterministic Ada core that is free to ship offline is: (1) the GNAT compiler itself (`-gnatwa -gnatwe -gnaty…`, plus `pragma Restrictions`/`pragma Profile (Ravenscar|Jorvik)` in a `gnat.adc` config, which turns coding rules into hard compile errors); (2) GNATprove (GPL-3.0, from Alire / GNAT-FSF-builds); and (3) GNATcheck, whose source is GPL-3.0 on GitHub (AdaCore/gnatcheck, ~216 LKQL rule files plus ~125 "KP" known-problem rules, TEXT/SARIF 2.1.0 output) but has no binary in Ubuntu or obvious community binary. AdaControl (GPL-2.0; GMGPL in older announcements) is effectively stalled (last binary 1.22r16c built for GNAT CE 2019; Ubuntu package dropped after 22.04). The AQ&S text is the only long-form open style guide; its original 1990s licensing is murky, while the Wikibooks "Ada Style Guide" derivative is CC BY-SA.

### Cited Findings
**Standards / guides**
- Ada Quality and Style Guide (AQ&S): a Usenet post reports the Software Productivity Consortium with the Ada Joint Program Office (AJPO) announced AQ&S "was now placed in the public domain" — [comp.lang.ada post](https://usenet.ada-lang.io/comp.lang.ada/815@ajpo.sei.cmu.edu/T); a 2002 thread instead quotes a copyright notice with a licence for unlimited use on the Ada 95 edition and does not settle the status — [comp.lang.ada 2002](https://usenet.ada-lang.io/comp.lang.ada/mailman.1031157842.31918.comp.lang.ada@ada.eu.org).
- The Wikibooks "Ada Style Guide" (a ~2012 update of AQ&S) is made possible "under the terms of the DoD Ada Joint Program Office's royalty-free, worldwide, non-exclusive, irrevocable license for unlimited use" of the Ada 83/95 style guides; Wikibooks content is CC BY-SA; ada-lang.io hosts an adapted copy stating it is adapted from Wikibooks under CC BY-SA — [Wikibooks Ada Style Guide](https://en.wikibooks.org/wiki/Ada_Style_Guide); [ada-lang.io copy](https://ada-lang.io/docs/style-guide/Ada_Style_Guide) (via search; ada-lang.io blocked here).
- A DTIC-hosted PDF of an AQ&S edition exists — [DTIC ADA241772](https://apps.dtic.mil/sti/tr/pdf/ADA241772.pdf) (search result; not opened).
- ISO/IEC TR 15942:2000 (Guide for the use of Ada in high-integrity systems): on 7 March 2005 JTC 1 recommended it be made freely available; SC 22 and JTC 1 approved and it "was implemented" — [WG9 N483r](https://open-std.org/jtc1/sc22/wg9/n483r.htm); a WG9 projects page lists it as publicly available at the ISO site (undated page) — [WG9 projects](https://open-std.org/JTC1/SC22/WG9/projects.htm). I found no withdrawal notice.
- ISO/IEC TR 24718:2005 (Ravenscar profile guide) is listed as withdrawn and "Superseded by ISO/IEC TS 24718:2025" — [standards.ie](https://shop.standards.ie/en-ie/standards/iso-iec-tr-24718-2005-614377_saig_iso_iso_1409771).
- ISO/IEC TR 24772-2:2020 (Ada vulnerabilities), first edition, published April 2020, 45 pages, JTC 1/SC 22; a paid ISO document — [ISO 71092](https://www.iso.org/standard/71092.html); [IEC webstore](https://webstore.iec.ch/publication/66889).
- Ada 2022 RM H.4 defines high-integrity restrictions including No_Allocators, No_Local_Allocators, No_Exceptions (no raise statements or handlers; no language-defined checks generated; execution erroneous if a check would fail) and No_Recursion — [Ada 2022 RM H.4](https://ada-rapporteur-group.github.io/ARM/Ada_2022/RM-H-4.html) (search snippet; site not fetched).
- Jorvik is the Ada 2022 relaxation of Ravenscar: a handful of Ravenscar restrictions removed or replaced, e.g. Simple_Barriers replaced by Pure_Barriers — [AdaCore blog, Introduction to Jorvik (2021, pre-final)](https://blog.adacore.com/introduction-to-jorvik).

**GNAT compiler as a deterministic checker** (local: `gnatmake` 13.3.0 help, Ubuntu apt `gnat-13` 13.3.0-6ubuntu2~24.04.1; `gnat` metapackage 13.2, `gnat-14` 14.2.0 also available)
- `-gnatwa` = "turn on all info/warnings marked below with +"; `-gnatw.e` = "turn on every optional info/warning (no exceptions)"; `-gnatwe` = "treat all warnings (but not info) as errors"; `-gnatw.d` tags each warning with its switch; `-gnatws` suppresses all — local: `gnatmake` help.
- `-gnaty` = default style checks "same as -gnaty3abcefhiklmnprst"; `-gnatyg` = "standard GNAT style rules, same as ydISux"; individual letters include `Mnn` max line length, `Lnn` max nesting, `O` overriding indicators, `B` no AND/OR for booleans (use short-circuit), `x` extra parentheses, `I` check mode `in` — local: `gnatmake` help.
- Other switches: `-gnata` (enable assertions), `-gnato` (overflow checks, default STRICT), `-gnatp` (suppress all checks), `-gnatE` (dynamic elaboration), `-gnat83/95/2005/2012/2022` (2012 default in GNAT 13) — local: `gnatmake` help.
- Test: a `gnat.adc` with `pragma Profile (Jorvik); pragma Restrictions (No_Allocators, No_Recursion, No_Exceptions, No_Implicit_Heap_Allocations)` compiled with `-gnatc -gnatwa -gnatwe -gnaty -gnatec=gnat.adc` produced `error: violation of restriction "No_Allocators" at gnat.adc:2`, the same for No_Recursion (direct recursion) and No_Exceptions (raise statement), plus `warning: … could be declared constant [-gnatwk]` and `(style) subprogram body has no previous spec` — local: GNAT 13.3.0 run 2026-11-05.
- `-fdiagnostics-format=sarif-file` produced **no** SARIF file for Ada (front-end diagnostics still printed as text) on GNAT 13.3 — local test. Conclusion: GNAT compiler output must be parsed from the stable `file:line:col: severity: message [-gnatwX]` text form.

**GNATcheck (LKQL-based)**
- GNATcheck and GNATkp now live in a dedicated repo (moved out of langkit-query-language); GNATcheck "checks Ada source files against a set of syntactic and semantic rules… Rules are written in LKQL; GNATcheck ships with a set of predefined rules, and users may write their own"; GNATkp (known-problem detector) "is a special packaging of GNATcheck available to GNAT Pro Assurance customers" — [AdaCore/gnatcheck README](https://github.com/AdaCore/gnatcheck) (HEAD 2026-10-29).
- Licence: repo root carries COPYING3 (GPL v3) and COPYING.RUNTIME — [AdaCore/gnatcheck](https://github.com/AdaCore/gnatcheck); the GNATcheck Reference Manual is under the GNU FDL — [GNATcheck RM](https://docs.adacore.com/live/wave/lkql/html/gnatcheck_rm/gnatcheck_rm.html) (via search).
- Rule set: `lkql_checker/share` contains ~341 `.lkql` files: 125 `kp_*` known-problem rules and ~216 others (some may be helpers), with names such as `goto_statements`, `recursive_subprograms`, `global_variables`, `float_equality_checks`, `others_in_exception_handlers`, `unchecked_conversions_as_actuals`, `maximum_parameters`, `metrics_cyclomatic_complexity`, `restrictions`, `style_checks`, `warnings`, `use_clauses`, `volatile_objects_without_address_clauses`, `non_short_circuit_operators`, `identifier_casing` — [AdaCore/gnatcheck lkql_checker](https://github.com/AdaCore/gnatcheck/tree/master/lkql_checker).
- The LKQL driver supports `--format=TEXT` or `--format=SARIF` ("A JSON output following the SARIF 2.1.0 scheme"), SARIF-carried auto-fixes (`--auto-fix-mode=IN_REPORT`) and a `patch` sub-command; docs also mention XML reports — [gnatcheck user_manual/source/lkql_driver.rst](https://github.com/AdaCore/gnatcheck/blob/master/user_manual/source/lkql_driver.rst).
- Building requires Libadalang/Langkit (the LKQL repo recommends the `ancr` dev environment) — [AdaCore/langkit-query-language](https://github.com/AdaCore/langkit-query-language). No `libadalang`, `libadalang-tools` or `gnatcheck` package exists in Ubuntu 24.04 — local: `apt-cache policy`.

**AdaControl (Adalog)**
- SourceForge lists AdaControl under GPLv2; latest downloadable file `adactl-1.22r16c-exe_linux_ce2019.tgz`; project "Last Update" 2022-09-08; claims "over 500" checks, multiple report formats, GPS/GnatHub integration — [SourceForge adacontrol](https://sourceforge.net/projects/adacontrol/).
- 1.22r15 announcement (22 Sep 2021): 73 rules, 591 possible checks; new "known exceptions" rule; custom output format; installation changed due to AdaCore no longer providing ASIS to the community — [comp.lang.ada announcement](https://usenet.ada-lang.io/comp.lang.ada/sig4f4$noc$1@dont-email.me/T).
- Older Adalog announcements described AdaControl as "fully GMGPL"; Debian's copyright file says GPL v2 or later — [AdaControl 1.5 announcement](https://usenet.ada-lang.io/comp.lang.ada/i58jge.6a5.ln@hunter.axlog.fr/T); [Ubuntu debian/copyright](https://bazaar.launchpad.net/~ubuntu-branches/ubuntu/trusty/adacontrol/trusty/revision/14/debian/copyright).
- Ubuntu 22.04 (jammy) packaged `adacontrol 1.21r6b-7` — [manpages.ubuntu.com jammy adactl](https://manpages.ubuntu.com/manpages/jammy/man1/adactl.1.html); it is absent from Ubuntu 24.04 — local: `apt-cache policy adacontrol` (not found).

### Inferences
- Highest-value offline Ada checks: a curated `gnat.adc` (Restrictions/Profile) + `-gnatwa -gnatw.d -gnatwe -gnatyg` (or a project style string) are 100% deterministic, ship with Ubuntu's `gnat-13/14`, and give rule-tagged messages. Pragma Restrictions effectively implement much of TR 15942/TR 24772-2 "subset" advice (no allocators, no recursion, no exceptions, Ravenscar/Jorvik tasking) as compile errors.
- GNATcheck is the best open rule engine (GPL-3.0, SARIF) but must be built from source against Libadalang; budget a build step or Alire-based install rather than apt. AdaControl depends on ASIS, which AdaCore stopped distributing to the community, so treat it as legacy.
- AQ&S rule text: redistributing the Wikibooks derivative is safe under CC BY-SA (share-alike applies to the text); for the original AQ&S, store citations and paraphrased checks unless the licence is confirmed.

### Gaps
- Could not open adalog.fr to get the current AdaControl rule list or confirm whether a Libadalang-based AdaControl exists in 2025–2026.
- Did not confirm whether a prebuilt community GNATcheck binary exists in Alire (`alr` index) in 2026; the README says nothing about community availability.
- Exact Jorvik restriction list (Ada 2022 RM D.13) not retrieved (ada-lang.io and ARM site blocked); GNAT 13 accepted `pragma Profile (Jorvik)` in the local test.
- Whether newer GNAT (GCC 14/15/16) emits SARIF for Ada was not tested; GNAT 13.3 did not.
- No source found on whether TR 24772-2 or TR 15942 are in ISO's free "Publicly Available Standards" list today (the WG9 page says TR 15942 is).

## Fortran: gfortran conformance flags, open linters/formatters, best-practice guides

### Takeaway
gfortran (GPL, Ubuntu `gfortran` 13.2/`gfortran-14`) gives a strong deterministic baseline (`-std=f2018 -Wall -Wextra -fimplicit-none -Wimplicit-interface -fcheck=all`) and, since GCC 13, SARIF 2.1.0 output via `-fdiagnostics-format=sarif-file`. Fortitude (MIT, Rust, PyPI `fortitude-lint`, v0.10.1, ~107 stable rules with IDs like C001/S061/OB…/MOD…/PORT…, SARIF/JSON/JUnit and more) is the clear first-choice open linter. fortran-lang.org's Best Practices mini-book is MIT-licensed. Others: fprettify (GPL-3.0, formatter), CamFort (Apache-2.0, units/stencil verification), cphyc fortran-linter (GPL-2.0), flinter (CERFACS; licence unverified), fortls (MIT LSP). FTorch is a PyTorch-Fortran coupling library, not a checker.

### Cited Findings
- gfortran 13.3 dialects: `-std=f95, f2003, f2008, f2008ts, f2018, gnu, legacy` (no f2023 in 13.x); relevant warnings include `-Waliasing`, `-Wcharacter-truncation`, `-Wcompare-reals`, `-Wconversion-extra`, `-Wimplicit-interface`, `-Wimplicit-procedure`, `-Wintrinsic-shadow`, `-Wline-truncation`, `-Wrealloc-lhs(-all)`, `-Wsurprising`, `-Wtabs`, `-Wunused-dummy-argument`, `-Wuse-without-only`; `-fcheck=[...]` selects runtime checks; `-fimplicit-none` forbids implicit typing; `gfortran --help=warnings` lists 440 `-W` options — local: `gfortran --help=fortran` / `--help=warnings`, GNU Fortran 13.3.0.
- Local test: `-std=f2018 -Wall -Wextra -fimplicit-none -fcheck=all` reported `Symbol 'x' … has no IMPLICIT type` (error) and a compile-time out-of-bounds warning (`4 > 3` in a loop) — local run 2026-11-05.
- `gfortran -fdiagnostics-format=sarif-file` wrote `t.f90.sarif` (SARIF version 2.1.0, driver name "GNU Fortran2008"); caution: in that run it reported `Function 'program' requires an argument list` which the identical text-mode run did not report — verify SARIF mode on your gfortran version before relying on it — local run.
- Ubuntu 24.04 packages: `gfortran` 4:13.2.0-7ubuntu1, `gfortran-14` 14.2.0, `findent` 4.3.2-1 (indenter/converter); no `fprettify`, `camfort` or `flint` packages — local: `apt-cache policy`.
- Fortitude: MIT ("This work is distributed under the MIT License"; inspired by and reuses parts of ruff); install `pip install fortitude-lint`, `uv tool install fortitude-lint@latest`, standalone installers since 0.7.0, or `cargo install --path crates/fortitude`; config in `fortitude.toml`/`.fortitude.toml`/`fpm.toml`/`pyproject.toml` with `select`, `ignore`, `line-length`, `preview`; "Over 100 rules" — [PlasmaFAIR/fortitude](https://github.com/PlasmaFAIR/fortitude).
- Fortitude version 0.10.1 (`crates/fortitude/Cargo.toml`, HEAD 2026-10-30); rule registry has 128 entries: Stable — Correctness 33, Style 32, Obsolescent 16, Fortitude 10, Modernisation 8, Portability 5, Error 3 (107 stable); Preview 14; Deprecated/Removed 7; category prefixes `E`, `C`, `OB`, `MOD`, `S`, `PORT`, `FORT` — [fortitude rules/mod.rs](https://github.com/PlasmaFAIR/fortitude/blob/main/crates/fortitude_linter/src/rules/mod.rs).
- Example stable Fortitude rules: C001 ImplicitTyping, C003 ImplicitExternalProcedures, C011 MissingDefaultCase, C022 ImplicitRealKind, C061 MissingIntent, C071 AssumedSize, C081 InitialisationInDeclaration (implicit SAVE), C092 ProcedureNotInModule, C121 UseAll, C131 MissingAccessibilityStatement, C181 UncheckedStat, C191 UnreachableStatement, MOD001 DoublePrecision, MOD021 DeprecatedRelationalOperator, MOD031 IncludeStatement, PORT011 LiteralKind, PORT021 StarKind, S001 LineTooLong, S061 UnnamedEndStatement, S071 MissingDoubleColon, S201 SuperfluousImplicitNone — [fortitude rules/mod.rs](https://github.com/PlasmaFAIR/fortitude/blob/main/crates/fortitude_linter/src/rules/mod.rs).
- Fortitude output formats: concise, full, json, json-lines, junit, grouped, github, gitlab, pylint, rdjson, azure, sarif — [fortitude settings.rs OutputFormat](https://github.com/PlasmaFAIR/fortitude/blob/main/crates/fortitude_linter/src/settings.rs).
- fortran-lang Best Practices mini-book ("a modern canonical way of doing things in Fortran… style guide and best practice recommendation"; chapters: Style Guide, Floating Point Numbers, Integer Division, Modules and Programs, Arrays, Allocatable Arrays, File I/O, etc.) lives in the `fortran-lang/webpage` repo, which is MIT-licensed ("Copyright (c) 2020-2022 fortran-lang.org Contributors") — [best_practices/index.md](https://github.com/fortran-lang/webpage/blob/main/source/learn/best_practices/index.md); [webpage LICENSE](https://github.com/fortran-lang/webpage/blob/main/LICENSE).
- fprettify (auto-formatter) is GPL v3 ("version 3 of the License"), © Patrick Seewald, CP2K developers — [pseewald/fprettify LICENSE](https://github.com/pseewald/fprettify/blob/master/LICENSE).
- CamFort, "a refactoring and verification tool for scientific Fortran programs", Apache-2.0; Homebrew install; Linux needs libflint, LAPACK, OpenBLAS, z3 — [camfort/camfort](https://github.com/camfort/camfort).
- cphyc/fortran-linter LICENSE file is GNU GPL version 2 text — [cphyc/fortran-linter LICENSE](https://github.com/cphyc/fortran-linter/blob/main/LICENSE).
- flinter: created at CERFACS for EXCELLERAT, named flinter because "flint" was taken; follows OMS Documentation Wiki conventions; became a multi-language linter from 0.6.0 — [PyPI flinter](https://pypi.org/project/flinter/) (licence not shown in results).
- fortls (Fortran language server) is MIT — [fortran-lang/fortls LICENSE](https://github.com/fortran-lang/fortls/blob/master/LICENSE).

### Inferences
- Recommended deterministic Fortran gate: gfortran `-std=f2018 -fimplicit-none -Wall -Wextra -Wimplicit-interface -Wimplicit-procedure -Wconversion -Werror` (compile-time) + `-fcheck=all` (test builds) + Fortitude (pin version, `--output-format=sarif`, explicit `select` list; keep `preview=false` for stability).
- Fortitude rule IDs map neatly onto fortran-lang best-practice topics (implicit none, intent, kinds, modules), so the MIT text can be cited alongside rule IDs.

### Gaps
- gcc.gnu.org was blocked; flag descriptions come from local `--help` output, not the manual.
- flinter licence and current maintenance status not verified (GitLab/PyPI page not opened).
- No public ISO/IEC 24772-8 (Fortran) text; it was a working draft in 2023–2024 (see TR 24772 section).

## COBOL: GnuCOBOL warnings/dialects, open analyzers, public standards

### Takeaway
There is no mature open-source COBOL linter. The deterministic options are GnuCOBOL's own `-W…` warnings plus its dialect configuration system (`-std=…`, `-conf=<file>`, `-f<feature>=<support>`), which can mark constructs such as ALTER or GO TO without a name as `error`/`obsolete`/`archaic`/`unconformable`, making a site COBOL standard enforceable at compile time. Che4z COBOL Language Support (EPL-2.0) gives syntax/semantic diagnostics via LSP; cobol-check (Apache-2.0) is a unit-test framework, not a linter. I found no publicly licensed mainframe COBOL coding standard.

### Cited Findings
- Local GnuCOBOL: `cobc (GnuCOBOL) 3.1.2.0`, GPLv3+; Ubuntu 24.04 packages `gnucobol3` 3.1.2-5.1ubuntu1, `gnucobol` (metapackage), `gnucobol4` 4.0~early~20200606 (early dev snapshot) — local: `cobc --version`, `apt-cache policy`.
- GnuCOBOL 3.2 was released 28 July 2023 (2.5+ years after 3.1.2) with reworked dialect handling — [info-gnu announcement](https://lists.gnu.org/archive/html/info-gnu/2023-07/msg00007.html); a SUSE package changelog (Jan 2026) notes 3.2 "changed defaults to better match the selected dialect" — [SUSE PackageHub](https://packagehub.suse.com/packages/gnucobol/3_2-bp160_1_1).
- cobc 3.1.2 dialects: `-std=default, cobol2014, cobol2002, cobol85, xopen, ibm-strict, ibm, mvs-strict, mvs, mf-strict, mf, bs2000-strict, bs2000, acu-strict, acu, rm-strict, rm` (config dir `/etc/gnucobol` also has `realia(-strict)` and `.words` reserved-word lists) — local: `cobc --help`, `ls /etc/gnucobol`.
- cobc warnings: `-Wall`, `-Wextra`, `-Wadditional`, `-Wobsolete`, `-Warchaic`, `-Wredefinition`, `-Wtruncate`, `-Wpossible-truncate`, `-Woverlap`, `-Wpossible-overlap`, `-Wparentheses` (AND within OR), `-Wstrict-typing`, `-Wimplicit-define`, `-Winitial-value`, `-Wprototypes`, `-Warithmetic-osvs`, `-Wcall-params`, `-Wconstant-expression`, `-Wcolumn-overflow`, `-Wterminator` (missing END-xxx), `-Wlinkage`, `-Wunreachable`, `-Wdangling-text`, `-Werror`, `-Werror=<warning>`; plus `-fsyntax-only`, `-fmax-errors=`, `-fstack-check`, `-fec=<exception>` — local: `cobc --help` (3.1.2).
- Dialect feature-support levels: values `ok, warning, archaic, obsolete, skip, ignore, error, unconformable`; e.g. `cobol2014.conf` sets `alter-statement: unconformable`, `goto-statement-without-name: unconformable`, `next-sentence-phrase: archaic`, `move-noninteger-to-alphanumeric: error`; `ibm-strict.conf` sets `alter-statement: obsolete`; `-conf=<file>` loads a user-defined dialect and `-f<feature>=<support>` overrides single features — local: `/etc/gnucobol/default.conf`, `cobol2014.conf`, `ibm-strict.conf`, `cobc --help`.
- No SARIF/JSON diagnostic output option appears in cobc 3.1.2 help — local: `cobc --help` (diagnostics are `file:line: warning/error: text`).
- Che4z COBOL Language Support: LSP-based autocomplete, highlighting and diagnostics ("syntax check… semantic analysis highlights incorrect names of variables, copybooks and paragraphs"), CICS/DB2/Datacom SQL support, IDMS add-on, remote copybooks via Zowe Explorer — [che-che4z-lsp-for-cobol README](https://github.com/eclipse-che4z/che-che4z-lsp-for-cobol); licence EPL-2.0 (`LICENSE.md`, `SPDX-License-Identifier: EPL-2.0`) — [LICENSE.md](https://github.com/eclipse-che4z/che-che4z-lsp-for-cobol/blob/development/LICENSE.md).
- cobol-check (Open Mainframe Project): "fine-grained unit testing/checking for Cobol", assertions, stubs/mocks, JUnit and HTML reports; Apache-2.0 — [openmainframeproject/cobol-check](https://github.com/openmainframeproject/cobol-check).
- cobol-intel: small third-party PyPI project for static analysis/call graphs/business-rule extraction with optional LLM explanations — [PyPI cobol-intel](https://pypi.org/project/cobol-intel/) (maturity unknown).

### Inferences
- A FORGE COBOL "coding standard" can be shipped as a GnuCOBOL `.conf` derived from `ibm-strict.conf`/`cobol2014.conf` with forbidden features set to `error`, plus `-Wall -Wextra -Werror=…` — fully deterministic and offline. Output must be parsed from text.
- Che4z's language server could be run headless for extra semantic diagnostics but is heavier (Java) and oriented to IDEs.

### Gaps
- gnucobol.sourceforge.io blocked: 3.2 NEWS (new warnings, any JSON/SARIF diagnostics) not read; local evidence is 3.1.2.
- No open, licensed public mainframe COBOL coding standard found (enterprise standards exist but none with a clear redistributable licence surfaced); IBM Enterprise COBOL compiler options (e.g. RULES) are proprietary to IBM's compiler.
- No open COBOL linter with stable rule IDs found.

## Rust: rustc/Clippy lints, API Guidelines, cargo-deny, cargo-audit/RustSec, Safety-Critical Rust Coding Guidelines, MISRA, Ferrocene

### Takeaway
Rust has the richest open, permissively licensed deterministic stack: rustc lint groups and Clippy (MIT/Apache-2.0, "over 800 lints" in groups correctness/suspicious/style/complexity/perf/pedantic/restriction/nursery/cargo), cargo-deny (MIT/Apache) and cargo-audit with the RustSec DB (data CC0, GHSA-imported parts CC BY 4.0). The Safety-Critical Rust Consortium's Coding Guidelines (code MIT/Apache-2.0, docs CC BY 4.0) are still early: tags up to 0.1.25, ~25 real guidelines all `draft`, MISRA-style categories, a MISRA C:2025 and CERT C cross-reference; MISRA has only an Addendum 6 applicability study, not a "MISRA Rust". Ferrocene (MIT/Apache) is a qualified compiler, and the FLS gives paragraph IDs that guidelines reference.

### Cited Findings
- Clippy: "There are over 800 lints"; groups `clippy::all` (correctness, suspicious, style, complexity, perf; warn/deny), `correctness` (deny), `suspicious`/`style`/`complexity`/`perf` (warn), `pedantic`/`restriction`/`nursery`/`cargo` (allow); `-D clippy::all` makes them errors — [rust-clippy README](https://github.com/rust-lang/rust-clippy); licence Apache-2.0 OR MIT — [rust-clippy COPYRIGHT](https://github.com/rust-lang/rust-clippy/blob/master/COPYRIGHT).

## Assembly and JOVIAL: any open standards or checkers?

### Takeaway
Honest answer: there is no widely adopted open coding standard for assembly language, and none at all for JOVIAL beyond the language standard MIL-STD-1589C. Checkers are niche: Go's vet `asmdecl`/`framepointer` analyzers check Go assembly; small linters exist for specific assemblers (m68k-lint, MIT, 132 rules, JSON output; naslint for NASM, stale since 2021); the SCRC Rust guidelines have an inline-assembly chapter. For JOVIAL there are two hobby J73 compilers on GitHub (now Apache-2.0) that could serve as a parser front end, but nothing resembling a linter.

### Cited Findings
- go vet includes `asmdecl` ("report mismatches between assembly files and Go declarations") and `framepointer` ("report assembly that clobbers the frame pointer before saving it") — local: `go tool vet help` (Go 1.24.7).
- m68k-lint: "132 built-in rules across correctness, suspicious-construct, optimization and…"; presets `recommended`, `style`; per-rule override `off|error|warning|suggestion|info`; `--format pretty|json`; MIT licence (© 2026 Graham Bates); npm, Node 20+ — [grahambates/m68k-lint](https://github.com/grahambates/m68k-lint).
- naslint (NASM style linter, Rust, MIT/Apache-2.0, last release Feb 2021); jhu-assembly-linter (course style checker); masmlint is for Miden VM assembly, not x86 MASM — [naslint](https://lib.rs/crates/naslint); [jhu-assembly-linter](https://pypi.org/project/jhu-assembly-linter) (via search).
- Ubuntu 24.04 has assemblers `nasm` 2.16.01 and `yasm` 1.3.0 (warning flags only, no style rules) — local: `apt-cache policy`.
- SCRC Rust guidelines contain an `inline-assembly` chapter directory — [src/coding-guidelines](https://github.com/rustfoundation/safety-critical-rust-coding-guidelines/tree/main/src/coding-guidelines).
- MIL-STD-1589C (USAF), dated 6 July 1984, defines JOVIAL J73; listed as inactive on EverySpec — [EverySpec MIL-STD-1589C](https://everyspec.com/MIL-STD/MIL-STD-1500-1599/MIL-STD-1589C_14577/); as of 2010 JOVIAL is no longer maintained/distributed by the USAF JOVIAL Program Office — [Wikipedia JOVIAL](https://en.wikipedia.org/wiki/JOVIAL).
- Skyhawk: "A compiler for JOVIAL J73 (MIL-STD-1589C), written in C99", stages incl. sema/typed AST/TABLE layout, x86-64 backend, ARM and MIL-STD-1750A backends planned, `make test` runs 209 tests; licence now Apache-2.0 ("Do whatever you want with it") — [Zaneham/skyhawk](https://github.com/Zaneham/skyhawk). jovial-compiler (Rust + LLVM 18) is also Apache-2.0 per current LICENSE/README — [Zaneham/jovial-compiler](https://github.com/Zaneham/jovial-compiler). Search snippets described both as Business Source License, so the licence was changed at some point — conflicting older info.

### Inferences
- For assembly, the deterministic options are assembler warnings (`nasm -w+all`, GNU as `--fatal-warnings`), ABI/calling-convention checks you write yourself, and per-ISA linters like m68k-lint; any "assembly standard" in FORGE will be house rules (header comments, register-save conventions, no self-modifying code) rather than an adopted public standard.
- For JOVIAL J73, the realistic route is building rule checks on top of a parser such as Skyhawk's (Apache-2.0), using MIL-STD-1589C as the reference grammar.

### Gaps
- No open assembly linter for PowerPC or MIL-STD-1750A found; did not check Linux kernel `objtool` or LLVM `llvm-mc` diagnostics in this session.
- No JOVIAL coding standard (e.g. historic USAF programming standards) found in public form; DTIC may hold 1970s–80s JOVIAL programming guides but none were located.
- MISRA C's assembly-encapsulation directives exist only in the paid MISRA documents (not checked here).

## ISO/IEC TR 24772 series (programming language vulnerabilities): parts, availability, cost

### Takeaway
ISO/IEC 24772-1:2024 (language-independent catalogue, 153 pp., published 29 Oct 2024) replaced TR 24772-1:2019. Published language parts are TR 24772-2:2020 (Ada) and TR 24772-3:2020 (C); Python (renumbered to Part 3 in later plans) and Fortran (Part 8) were still working drafts in the latest convenor reports found (2023–2024). All published parts are paid ISO/IEC documents; WG 23 working drafts on open-std.org are the free route, so rule text can be cited, not redistributed.

### Cited Findings
- ISO/IEC 24772-1:2024 "Language-independent catalogue of vulnerabilities", published 29 Oct 2024, 153 pages, International Standard from JTC 1/SC 22, replaces ISO/IEC TR 24772-1:2019 — [ISO 83629](https://www.iso.org/standard/83629.html); [IEC webstore](https://webstore.iec.ch/en/publication/102760).
- ISO/IEC TR 24772-2:2020 (Ada), April 2020, 45 pages — [ISO 71092](https://www.iso.org/standard/71092.html); [IEC webstore](https://webstore.iec.ch/publication/66889).
- A 2023 WG 23 convenor report says WG 23 has produced three editions; latest TR 24772-1:2019, TR 24772-2:2020, TR 24772-3:2020 (C); it describes Part 8 as the Fortran part — [WG23 N1321 (2023)](https://www9.open-std.org/JTC1/SC22/WG23/docs/ISO-IECJTC1-SC22-WG23_N1321-convenors-report-20230907.pdf) (via search; open-std.org blocked for fetch).
- The September 2024 convenor report lists "ISO/IEC WD 24772-3 … Python" (working draft) and "ISO/IEC WD 24772-8 … Fortran"; a 2018 plan had Python as Part 4 — [WG23 N1415 (2024)](https://www.open-std.org/JTC1/SC22/WG23/docs/ISO-IECJTC1-SC22-WG23_N1415-convenors-report-20240911.pdf); [WG23 N0798 (2018)](https://www.open-std.org/JTC1/SC22/WG23/docs/ISO-IECJTC1-SC22-WG23_N0798-convenors-report-20180606.pdf) (both via search).

### Inferences
- For an offline assistant, store 24772 vulnerability identifiers/titles as metadata on checks, and link checks to ISO clause numbers rather than copying ISO text.

### Gaps
- Prices (CHF) for each part not retrieved (iso.org pages reached only via search).
- No 2025–2026 status found for Python/Fortran/Java/C++ parts; open-std.org was blocked, so the latest convenor report could not be opened.
- Whether any 24772 part is in ISO's free Publicly Available Standards list was not confirmed.
